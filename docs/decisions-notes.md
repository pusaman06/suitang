# 学习笔记与知识库 · 决策记录

> 2026-11-05 起。每条记「结论 + 理由」，理由比结论重要——三周后你会忘记为什么这么选。
> 状态：`已定` / `待定` / `已推翻`。

## 1. 产品形态

### D1 知识库在 DSH 里用 ✅ 已定

**结论**：主入口是 DSH 里的技能，不做独立浏览器页面、不做独立应用。

**理由**：用户每天已经在 DSH 里工作，边际成本最低。数据格式仍按「以后能长出可视化页面」来设计，留退路。

### D2 记录粒度：两层，先做视频层 ✅ 已定

**结论**：第一层是「一个视频一份笔记」（原始材料），第二层是从笔记里抽出的「概念卡片」，概念可以跨视频关联。

**理由**：直接按知识点记录会逼用户在看视频时就判断「这算不算一个知识点」，负担太重。先用视频层把材料攒起来，再用 AI 抽概念。

**代价**：概念层要等材料足够多才有价值，第一版可能只有视频层。

### D3 场景只做「事后查」 ✅ 已定

**结论**：不做「看新视频时主动提示你学过相关的 X」，也不做定期回顾推送。

**理由**：主动推荐需要语义检索 + 质量阈值，做不好就是噪音；噪音会让人把整个功能关掉。先把「我想查的时候查得到」做扎实。

### D4 落盘要由用户决定 ✅ 已定

**结论**：每个视频（或每一 P）有一个「记下来 / 不记」的开关，默认不记。

**理由**：用户原话——「有的视频我可能是随口喂，有的想确确实实做一个记录」。自动全量落盘会让知识库被垃圾视频淹没。

**待细化**：开关放在哪（面板常驻按钮 / 看完再决定）、默认值、已落盘的怎么反悔（删除）。

## 2. 笔记内容

### D5 笔记既是给机器读的，也是给自己看的 ✅ 已定

**结论**：落盘产物要有两种形态——结构化 JSON（给 DSH 技能检索）和 Markdown（人直接读）。Markdown 不只是字幕搬运，要能回答「我学到了什么」「我当时问了什么」。

**理由**：用户原话——「这个内容其实相当于一个笔记，不仅仅要给机器看，它甚至也要给我看」。

**已细化（2026-11-06）**：Markdown 只做资料索引——一句话摘要、基本信息、大纲、关键词、原文路径，外加「当时我问了什么」（真实问答，可选）。不再写「学到的点」「没懂的点」，见 D8。

### D8 笔记只做资料索引，不写「学到的」 ❌ 原结论已推翻

**原结论**（2026-11-05）：加「我学到了什么」（3–5 条要点）和「我的疑问」两段。

**改后结论（2026-11-06）**：两段都不加。AI 不替用户总结学到什么，也不替用户编疑问——那是读后感，编出来就是假的。

笔记只做**资料索引**：一句话摘要 / 基本信息 / 大纲 / 关键词 3–8 个 / 原文路径；**只保留一段「当时我问了什么」**，记录用户真的在面板里问过的问题和 AI 的回答，没问过就整段删掉。

**理由**：查了作者本人视频（`BV14FHP6LEJE` 字幕全文 45 行），他全程只演示界面、从没展示条目正文；唯一线索是 [02:30] 说搜出来的是「我之前那个录音导进去给它解析出来的」——**他入库的是原材料，靠命中片段读前后文检索，不是浓缩卡片**。插件本身也只硬性规定 frontmatter 六字段（`id/title/type/tags/status/created/updated`）和目录归属，没有正文范文。用户据此拍板按这个思路走。

**样子**：`_模板/视频笔记.md`；样板 `20-知识笔记/2026-11-05-我做了一个知识库插件（BV14FHP6LEJE）.md`。

### D9 内容 AI 先写一版，用户再改 ✅ 已定

**结论**：AI 生成初稿，用户看得见、改得动（Markdown 文件在硬盘上，直接用编辑器改）。

**理由**：用户原话「AI 先写一版，然后可以让我看一看，我自己来改」。纯手写成本太高，纯自动又不可信。

## 3. 与知识库对接

### D6 装 Personal-Knowledge-Base 插件，输出按它的规范直接入库 ✅ 已定

**结论**：装 `Personal-Knowledge-Base`（DSH 插件，不是那个 186MB 的 Electron 客户端），video-tutor 的产出按它的目录规范写进它的库，而不是只留在 `data/`。

**理由**：用户原话——「这个库实际上它不仅仅只是单纯的对接到我们这个 video 里面」，上课、上班的事也要记。分两套库等于自找麻烦。

**前提 ✅ 已验证（2026-11-06）**：直接往库里写的外部 md 会被 watcher 扫到并纳入索引（写入约 8 秒后 `kb_check` 报条目 +1），不需要先走「收件箱 → 整理」；`kb_search` 中文检索可用（插件 2.4.14 有个命中即报 `value is not lossless JSON` 的 bug，已打本地补丁修好，见 `default-workspace/docs/kb-search-hotfix.mjs`）。

### D7 面板常驻「记到知识库」按钮，默认不记 ✅ 已定

**结论**：开关放在面板上（不是看完弹窗），默认关。

**理由**：默认记会把「随口喂」的视频塞满库；弹窗会打断观看。

### D10 概念卡片批量抽，不逐视频抽 ✅ 已定

**结论**：不在每个视频结束时抽概念；攒够几个视频，或用户说「整理一下」时批量抽。

**理由**：逐视频抽要多一次模型调用，且新手视频里抽出来的多半是常识。批量抽还能顺手合并重复概念。

### D11 知识库没开时先存本地，补写做成按钮 ✅ 已定

**结论**：库服务不在线时，内容先写本地 `data/`，提供「把没同步的 N 条补进知识库」按钮；第一版不做自动补写队列。

**理由**：自动队列要处理冲突、重试、顺序，成本高；一个按钮已经够用。

### D12 「我的疑问」取消，只留真实问答 ❌ 原结论已推翻

**原结论**（2026-11-05）：问答里模型回答「视频里没讲到」的自动记成待查，另给一个「这里没懂」按钮。

**改后结论（2026-11-06）**：都不做。不自动记「没讲到」，也不做「这里没懂」按钮。库里只留**用户实际问过的问题和 AI 的回答**（笔记里的「当时我问了什么」段），没提问就没这段。

**理由**：两者都是在替用户「制造疑问」——「没讲到」是 AI 判断，不是用户想知道；按钮则假设用户会去点。用户明确说过不要 AI 提出一些问题。

## 4. 已定（2026-11-06 装完插件、建完库之后）

- **插件模板**：`_模板/` 里原有知识/项目/素材三份，都很简（标题 + 目标状态 + 进展）。我们另加了一份 `_模板/视频笔记.md`（带落库规则和骨架）。
- **视频笔记落 `20-知识笔记/`**，类型 `知识`；文件名由插件自动生成 `<日期>-<标题>.md`。日期原本按 UTC（晚上 8 点后入库会比本地早一天），已打本地补丁改成按本机时区，**需重启 DSH 生效**。多 P 课程一 P 一条笔记，课程级的分 P 列表不单独入库。
- **笔记结构（2026-11-06 第二次改，见第 6 节）**：一句话摘要 / **核心结论** / 大纲（**每章配 1–2 句内容说明**）/ 关键词 / 原文路径 /「当时我问了什么」（可选）。不写「我学到了什么」「我的疑问」。骨架见 `D:\knowledge-base\_模板\视频笔记.md`。
- **字幕全文不进库**：留在 video-tutor 的 `data/videos/<BV>/pN.md`，库里只给路径。理由：一集 8 分钟的字幕就有两三千字，几十集会淹没搜索；字幕是原始材料，按 BV 号能回本地查。
- **外部写入会被自动索引**（已验证：写进 `20-知识笔记/` 约 8 秒后 `kb_check` 条目 +1）。「收件箱归档前不建索引」只约束 `90-收件箱/` 里的原件。
- **概念卡片的第一个版本**：仍待定，等攒够几条视频笔记再按 D10 批量抽。
- **编辑体验**：先用编辑器直接改 md（D9）；校对完把 `status` 从「进行中」改成「已完成」。

已落库的样板：`20-知识笔记/2026-11-05-我做了一个知识库插件（BV14FHP6LEJE）.md`、`10-项目/2026-11-05-video-tutor.md`。

## 6. 大纲与笔记结构（2026-11-06 grill 后定）

> 2026-11-07 收口：D13 的「UP 章节优先」已删（章节骨架信息量低，用户确认收成 2 种方式），大纲现在只有「按字幕 / 按画面」。D14–D19 仍然有效。

### D13 分段来源：UP 章节优先，没章节才让模型按字幕切 ✅ 已定

**结论**：视频有 UP 章节（`view_points` ≥ 2 段）就直接用章节当大纲骨架，模型不再参与切段；没有章节才把字幕交给模型切。

**理由**：章节是 UP 手写的目录，免费、边界准；模型切段每次都要付一次调用，边界靠推断。用户原话「有 up 章节的时候，那就按这个 up 章节来当大纲。没有 up 章节的话，我们就需要去根据字幕来切大纲」。

**注意**：现在的代码是反的——有字幕就走模型切段，章节读都不读（`src/background/index.ts:1005-1020`）。要改。

### D14 模型切段改成「行号锚定」，时间戳由系统反查 ✅ 已定

**结论**：模型不再直接输出 `{start, end}` 秒数，只输出「从第 N 行切到第 M 行」；系统用字幕行的真实时间填充 start/end。

**理由**：模型写数字就是在编，没人校验；改成行号后时间戳永远来自字幕原文，不可能编错。借鉴自 Bilitato（`utils/promptBuilder.js:151`：「最终系统会以 start_line/end_line 映射到原始字幕时间为准」）。

### D15 字幕不抽稀，36000 字符才截断 ✅ 已定

**结论**：`compactCuesForOutline` 的预算从 14000 提到 **36000 字符**，超出部分从尾部丢弃（不抽稀）。

**理由**：14000 是当初拍脑袋定的保守值，不是模型能力限制。Bilitato 用的是 `MAX_SUBTITLE_CHARS = 36000`（`background.js:1112`），同样不做抽稀。DeepSeek 上下文 128K，52 分钟字幕约 2 万字、1 万 token，整段喂完全放得下。抽稀（等间隔丢行）反而会让模型看不到完整上下文。

### D16 每章下面写「这段讲了哪些事」，一次调用写全部章节 ✅ 已定

**结论**：在大纲每个章节标题下加 1–2 句内容说明，描述这一段讲了哪些事（不写结论）；所有章节的内容**一次调用**生成，不按章分次。

**理由**：用户原话「我光看大纲的话，我有时候还不一定想起来这个里面讲的是一个什么样的内容」——缺的是内容线索，不是第二个结论。一次调用省钱，且模型能看见前后文。

### D17 有章节没字幕时提示先转写，不抽帧 ✅ 已定

**结论**：有章节但没字幕时，面板提示「先点转写」，不自动抽帧。

**理由**：ASR 已确认免费（SenseVoiceSmall 0 元/千字符），转一次几分钟；抽帧贵、慢，画面也未必写着字。

### D18 核心结论用「总结式」，但不得引入字幕外信息 ✅ 已定

**结论**：核心结论由模型自由概括（不是逐条摘原句），硬约束是**不得引入字幕里没有的信息**；视频没有字幕时不生成这段，并在笔记底部注明。

**理由**：用户原话「52 分钟的视频想总结一句话，只从字幕里挑原句其实还是有一点点困难……尽量用它字幕里面的内容，但是还是以自由概括的形式」。摘句式做不到，强制带时间戳也没意义（一句话概括跨多个时间点）。

### D19 ASR 估算时间戳要标注 ✅ 已定

**结论**：底稿开头加一行说明，笔记的大纲段也加；逐条不加标记。

**理由**：ASR 的时间戳是按字数比例分配的估算值（`src/shared/asr.ts:80-116`：SiliconFlow 只返回整段 text，没有时间戳），跟官方字幕的真实时间不是一回事。用 UP 章节时不标（章节边界是 UP 给的，本来就不带时间戳语义）。

### 押后：Bilitato 的 Side Panel

用户注意到 Bilitato 用的是 Chrome 侧边栏（Side Panel），不挡视频、在旁边问问题更舒服。但侧边栏是浏览器级 UI，跟「以后要在其他网站用」不冲突（`chrome.sidePanel` 也是全局的），值得单独评估。**先做完上面的改造再聊。**
