# 本地落盘与知识库的合并（2026-11-06）

## 背景

原设计（D5）是双形态：本地落盘 `data/videos/<BV>/p1.json + p1.md` 与知识库笔记各自独立。
2026-11-06 的 grill 里，用户提出：落盘如果不省 token、回看又靠浏览器缓存，那它独立存在的意义是什么？

## 先确认的事实

1. 扩展读写全程走 `chrome.storage.local`（`src/shared/sync.ts:210` `readPageRecord`、`:222` `writePageRecord`），**磁盘上的 `data/videos/` 是单向导出，扩展从不回读**。
2. 回看旧视频时：字幕读 `sub:<bvid>:<p>:<cid>` 缓存、大纲读 page record，**0 token**，且与磁盘文件无关。
3. 所以「落盘省 token」不成立；落盘的真实价值只有「可导出」「可被别的工具读」「当知识库笔记的原文证据」。
4. 知识库插件把 `50-底稿` 硬编码为索引排除目录（`packages/kb-core/src/index-maintenance.js:55`）。实测（2026-11-06 08:15）：
   - 放进去的 md 不进全文索引、不进向量索引（搜「紫藤色留声机」零命中）；
   - `kb_check` 不统计它，无 frontmatter 也不报缺陷；
   - 从 `20-知识笔记/` 的笔记用相对链接指向它，`kb_check` 缺陷=0，不判断链。

## 已定

### 决策 1：本地落盘并入知识库，不再单独存在

**结论**：取消「项目目录下的 `data/videos/` 落盘」这条线，字幕与大纲原文改存进知识库的排除索引目录。

**理由**：落盘不省 token（扩展不读磁盘），回看靠 `chrome.storage` 缓存；它唯一不可替代的价值是当知识库笔记的原文证据。独立存在等于维护两套存储、两份失败队列。

### 决策 2：原文放 `50-底稿/视频原文/<BV号>/p<N>.md`，不被搜索命中，只能从笔记引用进去

**结论**：字幕全文与大纲原文落在 `50-底稿/视频原文/` 下；`20-知识笔记/` 里只放索引卡（摘要/大纲/关键词），末尾给一条绝对路径指向原文。

**理由**：`50-底稿` 是插件硬编码的排除目录，天生不进索引——用户要的「搜的时候只看到想存的文章，原文在后面放着，点链接才看得到」正好对上，不需要改插件。

**为什么按 BV 号而不按标题**：BV 号永久稳定、不含非法字符；标题会改、会重名、要清洗。

### 决策 3：落盘时机 = 按钮触发（2026-11-06 用户拍板）

**结论**：看视频不写盘。只有点「存到知识库 → 写入知识库」时，才同时写索引卡和原文底稿。

**理由**（用户原话）："正常人刷一个视频没必要存进去，浪费空间"；"只有当我选择存入我的知识库的时候，这些东西才有意义"。

### 决策 4：砍掉自动同步那套

**结论**：删除 `sync.ts` 的队列 / 失败重试 / 清空 / 面板「同步失败 N 条」/ 设置页「开启本地落盘同步」开关。`chrome.storage` 只留缓存与设置。

**理由**：没有自动落盘，就不存在「队列积压」「同步失败」这些状态；留着等于给用户一个永远不该出现的红字。

### 决策 5：缓存清理时字幕与问答一起清

**结论**：面板「清空记录」= 清问答历史 + 清该视频的 page record + 清字幕缓存。

**理由**（用户原话）："把这些字幕还有我的问答，清空的时候都给他清掉"——没存进知识库的东西就是随口一问，没必要留。
